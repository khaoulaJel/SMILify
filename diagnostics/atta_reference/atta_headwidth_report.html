01Methodology

Five phases, each reproducible from the paths in the appendix.

Data acquisition & indexing

The 20 Atta scans were located in the shared Google Drive (UM6P_2026/DATA/mesh_registration/ALL_ANTS_CLEAN), reachable directly from the cluster via a pre-configured rclone remote — no local round-trip needed. Filenames were already 01.obj–20.obj, matching the reference CSVs' shape labels exactly. Indexing was checked against the reference body lengths before fitting: correlation between each mesh's bounding-box extent and its reference b_t–b_a_5 length, r = 0.985.

Fitting recipe — A/B decision

Two candidate fitters were run head-to-head on the same 20 meshes, with the model file pinned identical between them (sha256-verified) so the fitter was the only variable:

Blender import

SMIL Model Importer, with the fitted npz loaded and every processing toggle off:

Result: 20 distinct shape keys named 01.obj–20.obj, each the fitter's raw per-specimen output.

Head-width reporter bones

Two bones, b_h_l / b_h_r, added as children of b_h, placed at the widest point of the head capsule on each side. Placed against the Basis (template) shape specifically — the exporter's nearest-vertex search reads mesh.vertices, which always holds Basis coordinates regardless of which shape key is displayed, so Basis is the only frame worth aligning a landmark against. Added after fitting, per Fabian's note that order doesn't matter — the bones are inert reporters, unrelated to pose or deformation.

Reference load & export

ant_body_lengths.csv loaded in the Morphometry panel (confirmed: Joint Pair: b_t to b_a_5 [mm], Number of Shapes: 20), then Joint Distances exported with the mesh selected.

02One deviation from spec

Stated plainly

Fabian's instruction: add the vertices to each bone's vertex group "e.g. via weight painting." This replication used the importer's default inverse_distance method instead — each bone automatically claims its 10 nearest vertices, weighted by distance — rather than painting weights by hand.

This is a substitution of method, not a corner cut: the tool supports both, and Fabian's own phrasing ("e.g.") frames weight painting as one example, not the only route. The validation in §3 is the justification — if the automatic method had grabbed the wrong vertices, it would show up as elevated head-width error relative to the rest of the skeleton, and it doesn't in a way that changes the verdict (see the allometry check below).

Is the error noise, or a real problem? — allometry check

Fitting Fabian's own 20 reference points to a log-log allometric line and checking whether the replicated points scatter around it any more than his own data does.

Fabian's reference Replicated (this work) allometric fit (on reference)
std(residual), Fabian's own data): 0.0232 log₁₀-units  ·  std(residual), replicated data: 0.0232 log₁₀-units — identical. The four specimens with the largest raw % error against the old CSV (03, 04, 06, 20) are not the ones sitting off the line — 03's residual is −0.004, essentially on it. Only 10 crosses a 2σ flag, and it was already the largest outlier in Fabian's own reference at that residual (0.057 vs. the replicated 0.050 — the new point sits closer to the line than his does). Verdict: the deviations from the old numbers are ordinary specimen-to-specimen scatter, not a systematic placement error — good enough for a scaling-law claim.

Where inverse_distance actually landed

No Blender access from the cluster to inspect this visually, so the bones' exact 3D position was reconstructed instead — by trilateration from the pairwise distances already in the export, against the pkl's known joint positions (well-conditioned; fit residual ≈0.013 model units).

Both b_h_l and b_h_r sit closer to the mandible base (ma_l/ma_r, ≈0.14 model units) than to the head-center pivot (b_h, ≈0.20) or the antenna base (≈0.18–0.27). Wilson (1980)'s head-width convention is nominally taken at eye level in full-face view — there's no eye landmark in this rig to check directly, so this can't be confirmed as an error, only noted: the grabbed point sits toward the mandibular/genal region rather than mid-head. Given the allometry check above shows the numbers land on the established scaling law, this reads as a one-line caveat for Fabian, not a fix to make.

04Bugs found along the way

Two defects in the existing addon, independent of this replication's result. Reported to Fabian separately, ahead of this document.

Blocks export

Inverted static_joint_locs guard

export_joint_distances in SMIL_processing_addon.py raises UnboundLocalError: J_regressor on origin/master for any model without a static_joint_locs key (including OmniAnt_25PCs_joint_limited.pkl) — the regressor is built only when the flag is true, but read only when it's false.

Traced to commit 6cde0d34 (2025-11-24), which added the same guard in six places — five correct, this one inverted. Fabian's reference CSVs predate that commit (2025-03-04), which is why his export worked and a fresh one couldn't.

Wrong numbers, not a crash

Constant scaling factor in SMPL_Object_measurements.csv

Every one of the 20 Atta scaling factors in that file implies the same b_t–b_a_5 distance (0.845) across all 20 specimens, while SMPL_Object_joint_distances.csv correctly varies it (0.590–0.920). export_mesh_measurements reads obj.data.vertices after setting a shape key's value, but shape keys only move the depsgraph-evaluated mesh — so it silently reads Basis every time. Surface-area/volume figures in that file are off by 8–43% depending on specimen.

Does not affect this document: every number above was checked against SMPL_Object_joint_distances.csv, which is unaffected — confirmed directly, not assumed.
